LHT Lab: an isolated second environment

A separate AWS account, repo and set of users where Matania can change the app freely, without access to the production server. Data and code move between the two environments only by a manual, reversible sync that both sides approve.

Some details are kept off this public page

Resource names, the AWS account ID and anything security-related are left out on purpose. Eliyahu sends them to Matania privately by email in LHT-Lab-private-notes.md. References like N1–N5 on this page point to sections of that file.

Summary

Both environments serve the same business. LAB is not a staging environment; it is a parallel copy of the product that may later be merged back or retired.

Goals

  • LAB runs in its own AWS account with its own bill, credentials, users and Cognito pool.
  • Nobody from LAB can reach MAIN's server, database or bucket unless MAIN grants it.
  • The catalog syncs both ways. Orders and customers sync from MAIN to LAB only. Conflicts are skipped and reported.
  • Every sync takes a backup first and can be reverted.
  • Code moves both ways through simple cherry-picks guided by a local skill.

Not in scope now

  • A proper staging environment.
  • Live or automatic replication between the two databases.
  • Merging the two apps back into one (decided in a few months).
  • Shared login: an employee has a separate account in each environment.

Architecture

Two standalone AWS accounts, with no AWS Organization between them, because an Organization means one paying account. They connect only through private "exchange" buckets that each side opens to the other.

The rule that keeps MAIN safe: each side only ever writes to its own account. To sync, the source side exports a package into its own exchange bucket. The target side reads that package through a read-only grant and applies it to its own database. Neither side ever holds the other's database password, SSH key or AWS keys.

Key decisions

The design choices. Your answers to the review questions are listed under Answered questions.

D1
Two standalone AWS accounts, linked by bucket policies

Each side grants the other account read access to its exchange bucket with a single bucket-policy statement. A sync only works while both sides keep their statement in place, so it needs both sides' agreement. Removing your statement cuts the link instantly. Every read is logged in CloudTrail.

D2
Record IDs never collide: LAB numbers start at 1,000,000,000

Both databases use auto-incrementing integer IDs. After the first copy, LAB moves every ID counter (Postgres sequence) up to 1,000,000,000, so a record's ID means the same thing in both environments. With unique IDs, a merge doesn't need to translate IDs between the two databases. Order numbers get the same treatment through the LAST_ORDER_NUMBER setting, so LAB orders start at 900000.

D3
Three-way merge against the last sync

Every sync stores a snapshot of the data at sync time. The next sync compares source, target and that baseline, so it can tell "only one side changed this" (apply it) apart from "both sides changed this" (a conflict).

D4
Dry run first, downtime second

The merge plan and conflict report are generated while both apps are still up. The target goes down only to take the backup and apply the plan you already reviewed.

D5
Matania mirrors the repo into a personal account, not a GitHub fork

Matania already has read access, and copies the full history with git clone --mirror and git push --mirror into a new private repo. When someone loses access to a private repo, GitHub deletes their forks of it, but a mirror survives. A full-history copy keeps the common ancestor, so cherry-picks work in both directions.

D6
Values that differ per environment move to environment variables, in MAIN first

The bucket name, image URL prefix, domain, email sender and AWS region are currently hardcoded in about 15 files. If both repos edit those lines differently, every future cherry-pick conflicts. LAB then takes this change as its first cherry-pick.

D7
LAB emails employees only

A new setting limits outgoing email to admin, editor and sales_rep users, so customers never receive a second copy. MAIN keeps it switched off.

Data sync

There are two sync modes, built in two stages. Full copy works from day one with standard tools. Merge sync is built once there is real divergence to merge.

Mode A: full copy (stage 1)

The target becomes an exact copy of the source: pg_dump → exchange bucket → pg_restore, plus an image sync. The target's own changes since the last sync are lost, so this mode is for the first setup and for resetting LAB. It is simple, reliable and fully reversible from the backup.

Mode B: merge sync (stage 2)

A small CLI in the repo (cmd/lhtsync) exports the synced tables as JSON plus a manifest: source environment, git commit, schema fingerprint, time and row counts. On the target it compares three versions of every record, looked up by ID:

changed only in sourceApply
changed only in targetKeep target
changed on both, same resultNothing to do
changed on both, differentlyConflict
new in sourceInsert
new on both, same SKU or emailConflict
soft-deleted (removed=true)Sync as a normal change
hard-deleted on one sideReported, not applied

Conflict handling

Each conflict lands in an HTML report. The default is skip and report. You can override it per record or per table:

  • skip leaves both sides as they are, and the conflict shows up again next time (the default).
  • source wins / target wins applies to the whole record.
  • field merge combines the two when the sides changed different fields of the same record, for example price on one side and description on the other.

The plan aborts before any downtime when the schema fingerprints don't match on a synced table. Examples are a column one side added, or an enum value the other side doesn't know. Those changes have to be cherry-picked across first, so code sync always comes before data sync.

Only the catalog flows from LAB back to MAIN, so a merge into MAIN only ever touches catalog tables. Orders created in LAB stay in LAB.

Maintenance window

Eliyahu runs every sync, on demand, after business hours, with a limit of 60 minutes. It runs on the target side, which is the environment receiving data. The source stays up because pg_dump reads a consistent snapshot. Catalog changes going back to MAIN need a second window on MAIN.

  1. Dry run, the day beforeGenerate the merge plan and conflict report, resolve conflicts, and freeze the plan. Both apps stay up.
  2. Announce the windowMessage employees with the time and expected length (up to 60 minutes, after business hours).
  3. Switch to maintenance mode app downStop the app container and serve a static "under maintenance" page on the same address. /health stays down so nobody mistakes it for the live app.
  4. Back up app downTake a manual RDS snapshot, plus a pg_dump into the exchange bucket. Record the backup IDs and the time in the sync log. Image versioning is already on.
  5. Apply app downMode A restores the package. Mode B applies the frozen plan inside one database transaction, so a failure rolls back automatically. Then sync the images.
  6. Verify app downStart the app. Compare row counts against the manifest. Smoke-test: log in, open the catalog, open one synced order, open one image.
  7. Reopen, or revert by minute 50If everything passes, remove the maintenance page. If anything fails, or verification isn't finished by minute 50, revert so the app is back within the hour.
Revert

Stop the app, then pg_restore the step-4 dump (or restore the RDS snapshot to a new instance and point the app at it). Delete the image files listed in the manifest, and start the app. A revert after the window reopens also discards whatever employees entered since, so the decision belongs inside the window. Backups are kept for 30 days.

Code sync

Manual and selective. There is no shared branch; each side decides what to take.

# once, in each repo
git remote add peer <the other repo's URL>   # fetch-only
git config rerere.enabled true                  # remember how a conflict was resolved

# each time
git fetch peer
git log --oneline main..peer/main --no-merges   # what they have that you don't
git cherry-pick -x <sha>                        # -x records the source commit

A local Claude skill, /peer-sync, wraps this so neither of you needs extra tooling:

  • Lists the peer's new commits, grouped and summarised in plain language.
  • Flags commits that touch ent/schema/, because these affect data sync, and commits that touch configuration or deploy scripts.
  • For each commit, offers to take it (cherry-pick), skip it, or study it (explain it so you can rewrite it your own way).
  • Records every decision in docs/PEER_SYNC_LOG.md, so skipped commits aren't offered again.

Ground rules for both sides: small commits that each do one thing, schema changes in their own commits, and no environment-specific values in code.

Risks

High
Credentials must be rotated before LAB goes live

Fix: Eliyahu’s Phase 0 (details in N2).

High
Automatic schema migration drops columns

Ent runs WithDropColumn(true), so a restore or cherry-pick from the other side can silently drop a column the receiving side still uses. Fix: the schema check aborts the plan; consider versioned migrations before stage 2.

Medium
Replacing MAIN’s images bucket policy breaks every image

The existing policy is what the live site depends on. Fix: add a statement, never paste over the policy; review it in the console.

Medium
A late revert loses employees' work

Fix: verify inside the window, keep the window short, and announce it.

Medium
Customers receive emails from both environments

Fix: LAB emails employees only (D7).
